The real defect was treating `readdir()` returning null with an I/O error as normal end-of-directory. Fault injection reproduced admission of a 41st item, false empty or partial inventory, and reused ordering ordinals. Existing committed bytes were preserved, but the scan result was unsafe. Both stores now clear `errno` immediately before each read and propagate an I/O error through `list`, `inventory`, `occupied`, and `assign_ordinal`. The same harness against frozen 163 reproduced 183 directory-error failures. The correction changes no storage schema, deletion rule, capacity, wire protocol, OTA behavior, or retry allowance.

Persistent corrupt-held metadata retains its previous handling: it is not automatically deleted and does not globally block every new capture. Ordering across corrupt metadata is therefore not guaranteed. Old and future timestamp records are retained; replay-age eligibility belongs to the runtime, not store eviction. Host POSIX faults do not qualify physical SD/FAT power loss or the ESP mount driver.

## Backend custody and the held-worker limit

The [backend stress results](</Users/MattTaylor/halo-device-analytics-2026-09-10/offline-stress-20260915/backend-host/RESULT.json>) distinguish accepted custody from completed work. A worker claim can commit while its response is lost, leaving accepted audio retained in the cloud with zero effects. An ambiguous or dead worker is held for manual review rather than automatically replaying potentially completed mutations. Thus an accepted `202` can legitimately allow device SD deletion without proving that the user's requested list change completed.

A narrow correction lets the **same live worker and claim token** recover its own lost claim response within the original observation window. Forty-six focused tests passed. The [deployment receipt](</Users/MattTaylor/halo-device-analytics-2026-09-10/offline-stress-20260915/backend-host/voice-claim-candidate001/deploy/DEPLOYMENT.json>) records one worker helper update with exact readback and unchanged configuration. Ingest/API configuration and existing jobs were not changed; historical ambiguous jobs are not reclaimed. The real voice receipt shows execution under the new helper, not an injected live lost-response recovery. Neither these mocks nor that device run establish exactly-once product semantics.

## Long-capture hardware failure and165 correction

Both164 applications were installed with protected-bank readback and later reported SDK `VALID`. A ten-second voice capture (319,488 bytes), Dish image (117,079 bytes), and Discard image (117,505 bytes) then exposed a real loss. During the45-second sleep flush, the voice save took about37 seconds. The worker next began saving Dish. Main simultaneously removed the queued Discard for its old timeout-rescue path. That second sender could not acquire the UART lease; two local admission refusals were treated as failed storage attempts, and main freed the only Discard buffer. The later sleep guard protected Dish but could not recover Discard. The [closed failure analysis](</Users/MattTaylor/halo-device-analytics-2026-09-10/offline-stress-20260915/hardware164-burst002/FAILURE-ANALYSIS.json>) retains the exact saved=0/lost=1 evidence. It is not a passing three-item burst.

The165 correction removes the main task's competing queue/parked rescue in production. Ordinary flush expiry leaves payload ownership with the upload worker and defers sleep. The next normal sleep attempt reopens the worker's drain gate. A small atomic claim covers the gap from dequeue through processing/free, so an empty queue plus a not-yet-set `upload_inflight` cannot look idle. The legacy background main drain remains only in the non-deferred configuration. Original deadlines, storage formats, UI, UART protocol and OTA are unchanged. The existing guardian hard stop remains an explicit boundary where RAM-only media can still be lost; this correction does not promise persistence through arbitrary power loss or that hard ceiling.

The [independent review](</Users/MattTaylor/halo-device-analytics-2026-09-10/offline-stress-20260915/custody165-peer001/RESULT.json>) and [primary regression receipt](</Users/MattTaylor/halo-device-analytics-2026-09-10/offline-stress-20260915/sleep-custody-fix001/RESULT.json>) cover actual source extracted into deterministic host fixtures. They reproduce164's loss, preserve the exact queued payload with the fix, exercise the later flush, claim gap, user cancellation, parked/held/inflight cases and legacy behavior. Worker/storage timing is modeled; hardware165 acceptance is still required.

The two retained164 items reached the cloud. The voice worker completed; Dish had exact cloud custody but its SD deletion acknowledgment was missed, so its SD copy remained pending. The failed Discard's exact cloud admission was absent at the recorded read. These results are separate from any later retry or corrected165 test: [cloud evidence](</Users/MattTaylor/halo-device-analytics-2026-09-10/offline-stress-20260915/cloud-burst164-001/>).

## Capacity latency boundary and a held follow-up

The [capacity experiment](</Users/MattTaylor/halo-device-analytics-2026-09-10/offline-stress-20260915/storage-host/list-capacity001/REVIEW.json>) uses the actual stores, 40 real 512-KiB files per media, and the actual LCD budget/WDT callback with **simulated**, uncalibrated read/CRC costs. LIST currently CRC-checks every matching payload: 20 MiB at maximum capacity. LCD allows 12 seconds for that work; Sense shares a 15-second LIST deadline across retries. The progress callback resets the watchdog and introduces no deliberate delay.

At modeled 0.5 ms/KiB plus 5 microseconds per watchdog callback, a full scan completes in about 10.35 seconds. At 0.6 ms/KiB it returns I/O failure after 38 complete items. No candidate is emitted; repeated scans of an unchanged slow backlog make no progress. All existing files remain intact. Four maximum-size items take about 2.06 seconds at 1 ms/KiB and 4.11 seconds at 2 ms/KiB, but also fail at sufficiently slow service. This does not demonstrate an actual unit throughput failure or establish that every queue of four is safe. The earlier 40-item fault tests used 1,536-byte payloads; their capacity correctness result did not qualify this timing boundary.

A [scratch-only proposal](</Users/MattTaylor/halo-device-analytics-2026-09-10/offline-stress-20260915/storage-host/list-capacity001/proposal001/REVIEW.json>) first orders metadata, then validates the oldest candidate, skipping corrupt candidates under the original deadline. It passes the original 206 store checks and 2,755 stress cases; the healthy maximum backlog reads roughly one payload instead of all 40. Pure metadata-only LIST was rejected because it advertises corrupt oldest payloads that the current FETCH path cannot advance past. Even the two-stage proposal changes aggregate LIST count/invalid semantics for unexamined payloads, and many large corrupt candidates can still exhaust its budget. Full inventory remains unchanged. This needs a separate reviewed contract change and physical timing validation; **it is not part of164 or installed firmware**.
