- Review resources for every firmware change using [Resource review](Arduino/HALOMAIN_rev1p5_modular/docs/RESOURCE_REVIEW.md). Record allocation size/capabilities, lifetime/ownership, concurrent use, failure behavior and user responsiveness; a copy-only change can record unchanged runtime ownership and its build delta. For resource-affecting changes, retain before/after artifact reports and relevant runtime measurements. The [both-board audit](Arduino/HALOMAIN_rev1p5_modular/docs/RESOURCE_AUDIT_20260922.md) contains proposals, not implemented fixes. Never reuse or modify held 212 artifacts for an optimization.
- For an explicitly approved production release, follow [Nightly OTA publication](Arduino/HALOMAIN_rev1p5_modular/docs/NIGHTLY_OTA_RELEASE.md). Promotion makes the pair available for each eligible 02:00 check; it does not change timers, force an immediate fleet update, or prove installation. Fresh provisioning/manual checks may update earlier.
- **Default to local development.** Read [Development and release](Arduino/HALOMAIN_rev1p5_modular/docs/DEVELOPMENT_AND_RELEASE.md). Build, flash, test, commit, and push-to-device requests do not authorize public OTA. Keep the current production latest unchanged until the user explicitly approves that candidate for production; historical publication authorization does not carry forward.
- Prepare local candidates with `tools/firmware_candidate.py`; record bench evidence separately. Only after explicit release approval use the current paired publisher with `--approve-production-version` for each production remote phase. Do not use historical publisher copies, the retired single-board CLIs, or direct cloud writes to bypass this boundary.
- The authoritative production project is `Arduino/HALOMAIN_rev1p5_modular`; read its `AGENTS.md`, `docs/RELEASE_224.md` and build instructions before changing firmware. Frozen 158 remains a separate recovery reference.
- Use `PRODUCTION_BASELINE.json` and `RELEASE_BASELINE.json.current_working_source` to verify the public release identity; they do not override the newer private checkpoint above. Continue private changes from that checkpoint or reviewed descendants, retaining the approved private fixes. `current_baseline` identifies the frozen158 recovery artifacts. Historical records and `Arduino/HALOMAIN_rev1` are not alternative current development baselines.
- Run `python3 -B tools/verify_frozen_baseline.py` from the production firmware directory before preparing new firmware. This read-only check verifies ancestry and retained artifact identity, not the correctness of uncommitted changes.
- Run the full host gate after firmware fixes, following `Arduino/HALOMAIN_rev1p5_modular/docs/REGRESSION_TESTING.md`. Before publication, the snapshot's complete passing `RESULT.json` must match both build proofs; supply it to the paired publisher with `--host-result`.
